# Bug fixes — 16 October 2026

The 16 findings in `BUG-WORKFLOW-AUDIT-2026-10-16.md` have been addressed in the root application source. Existing working-tree edits were preserved. Nothing has been deployed or committed.

## Changes

- **Findings 1–2:** CV uploads authorize the persisted review owner and payment status for every plan, including basic. An existing submission cannot be overwritten. Gateway payments must match a stored order's user, reference, amount, currency, type, plan, and customer email. Repeated callback/webhook delivery returns the same review.
- **Finding 3:** Missing payment credentials return failure. Automatic successful mock transactions were removed. Gateway initialization now sends the generated order reference explicitly.
- **Finding 4:** The paid AI gate recognizes the application's `job_seeker` account type, while retaining compatibility with `candidate`.
- **Finding 5:** Proration accepts only payments for the subscription's plan and purchase type, linked by subscription ID or, for legacy records, its activation time. New purchases preserve the subscription's full value, including carried upgrade credit. Unrelated payments cannot become upgrade credit.
- **Finding 6:** Subscription pricing rejects nonpositive and unsupported durations. Wallet checkout also rejects fractional durations and invalid prices before charging or replacing a subscription.
- **Finding 7:** Both CV wallet purchase entry points create a paid review and redirect to its upload page. Debit, payment record, and entitlement commit together; failure rolls them back.
- **Finding 8:** Wallet purchases serialize on the user's database row. Existing course enrollments and webinar registrations are checked before charging. The generic checkout also accepts an idempotency key for retrying the same purchase.
- **Finding 9:** Saved-job removal now has a handler that deletes only the authenticated user's saved record.
- **Findings 10–12:** HTTP and command-line email workers share one implementation. Job type is read from the stored payload, scheduled availability is respected, failures retry with backoff up to three attempts, and atomic claims prevent overlapping workers from owning the same job. Expired claims can be recovered; stale owners cannot acknowledge a replacement claim. Candidates are scanned in bounded batches.
- **Finding 13:** Payment model writes preserve plan linkage and gateway audit fields. The current employer subscription callback also records its plan and subscription linkage.
- **Findings 14–15:** Both signed webhook URLs and the browser callback use the same wallet/CV fulfillment service. Wallet funding no longer depends on the browser returning. Error redirects determine account type before use.
- **Finding 16:** Candidate inactivity archiving includes `job_seeker` and returns affected-row counts.

The broader tests exposed two additional defects, also corrected: optional profile sections prevented a fully completed core profile from reaching 100%, and image-model tests omitted their authentication migration dependency. Reminder workers were aligned with the registration model's object return type and permitted reminder fields.

## Deployment and remaining limits

1. Apply the new `2026-10-16-000001_AddQueueLeases` migration before starting the updated queue workers. Drain/stop old workers during rollout so they cannot bypass the new claim rules. The migration was tested in an isolated test database; the application/production database was not migrated here.
2. Deploy the root `app` code through the normal release process. Duplicate copies under `auth/app`, deployment archives, and FTP staging folders were not edited.
3. Use gateway test mode to verify an actual CV checkout and wallet deposit against the deployed webhook configuration. No real payments or outgoing emails were sent during verification.
4. Historical payments with missing plan/order metadata, prior duplicate charges, and old successful CV wallet purchases without review records need data reconciliation. The patch prevents new occurrences; it does not guess missing financial records or alter customer balances.
5. Email delivery uses leases and retries. As with ordinary SMTP queues, a process crash after the mail server accepts a message but before local acknowledgment can still lead to a retry; strict exactly-once delivery requires provider-side idempotency.
