## 1. Technical Debt Eradication (Do This First)

Nothing else in this guide can be implemented cleanly until this section is done.

### 1.1 Inline Styles
An audit of `app/Views/` found 775+ instances of hardcoded inline styling (e.g. `style="border-left: 4px solid #F5A623;"`, `style="width: 140px;"`). These override global CSS, break mobile responsiveness, and make theming (including dark mode) impossible since inline styles can't respond to a CSS variable switch.

- Search the codebase for every `style="..."` attribute and migrate it to either a Bootstrap 5 utility class or a custom CSS variable / utility class from Section 2.
- Do this file by file and re-test each view after migration — don't do a blind find-and-replace, since some inline styles may be conditionally generated by PHP logic.

### 1.2 Native `alert()` Ban
Core flows (applications, saving jobs, messaging) currently call native browser `alert('Success')`. These block the main thread and look unprofessional.

- Replace every native `alert()` call with the existing `toastr` library (already loaded in the project) or an inline success state where appropriate.
- Audit `app/Views/admin/` particularly closely — admin flows tend to have the most legacy `alert()` calls.

### 1.3 Accessibility (a11y)
- Add `alt` attributes to every `<img>` tag missing one.
- Audit color contrast on all colored buttons (especially `--accent-orange-gold` on white, and white text on `--primary-navy`) against WCAG AA.
- Add `aria-label` to icon-only buttons (bookmark/save icons, hamburger menu, theme toggle).

### 1.4 Non-Responsive Forms
- Find every hardcoded pixel width on `<select>` and `<input>` elements causing mobile overflow ("right-tilt" layout shift).
- Rewrite using fluid Bootstrap grid classes (`col-12`, `col-md-6`, etc.) instead of fixed widths.

## 2. Design System Foundation

### 2.1 Typography
- **Headings (`h1`–`h6`):** Plus Jakarta Sans, loaded once, consolidated.
- **Body, forms, dashboard grids:** Inter.
- Remove every duplicate/conflicting Google Font `<link>` across `assets/css/style.css`, `public/css/style.css`, and `admin/layouts/app.php` (including the stray `Outfit` import). One consolidated font declaration in the core template only.

### 2.2 CSS Variable Architecture
Declare the brand palette and core tokens in `:root`. This is the single source of truth — no hex codes should appear anywhere else in the codebase after this is in place.

```css
:root {
  /* Brand Palette */
  --primary-navy: #002D5B;
  --primary-trust-blue: #005DA8;
  --accent-orange-gold: #F5A623;
  --accent-green: #10B981;

  /* Backgrounds & Text */
  --bg-white: #FFFFFF;
  --bg-light-gray: #F8F9FA;
  --text-slate-900: #1E293B;
  --text-slate-500: #64748B;

  /* Borders & Shadows */
  --border-radius-lg: 16px;
  --border-radius-md: 10px;
  --border-radius-sm: 6px;
  --shadow-soft: 0 4px 20px rgba(0, 0, 0, 0.05);
}
```

This variable layer is also the foundation Section 3 (Dark Mode) builds on — every color reference in component CSS must use `var(--token-name)`, never a raw hex value, or the dark theme override won't reach it.

### 2.3 Component Aesthetics
- **Glassmorphic utility:** define once, reuse everywhere — don't redeclare blur filters inline.
  ```css
  .card-glass {
    background: rgba(255, 255, 255, 0.45);
    backdrop-filter: blur(10px);
    -webkit-backdrop-filter: blur(10px);
    border: 1px solid rgba(255, 255, 255, 0.2);
    border-radius: var(--border-radius-lg);
  }
  ```
- **Border radius rule:** `6px–8px` for action items (buttons, inputs), `12px–16px` for structural elements (cards, containers). No exceptions.
- **Icons:** migrate all layout icons to Tabler Icons. Remove FontAwesome/UIcons references once migration is verified complete, to reduce payload.

## 3. Dark Mode Implementation

This is a real, shipped feature — not just CSS variables waiting to be used later. By the end of this milestone, every page (including all three dashboards) must render correctly in both themes, with a working toggle.

### 3.1 Toggle Mechanism
- Place a sun/moon toggle (Tabler `ti-sun` / `ti-moon`) in the header, near the login/CTA buttons, visible on both the logged-out and logged-in (dashboard) header states.
- On click, toggle a `data-theme="dark"` attribute on `<html>` (or a `.dark-mode` class on `<body>` — pick one convention and use it consistently).

### 3.2 Dark Token Set
Define dark equivalents for every token in Section 2.2 under the dark selector:

```css
[data-theme="dark"] {
  --bg-white: #0F172A;
  --bg-light-gray: #1E293B;
  --text-slate-900: #F1F5F9;
  --text-slate-500: #94A3B8;
  /* primary-navy / trust-blue / accent-orange-gold can stay largely
     the same since the brand hero sections are already dark */
}
```

### 3.3 Persistence & Flash Prevention
- Store the user's preference in `localStorage` (e.g. key `jr-theme`).
- To prevent a flash of the wrong theme on page load, add a small inline `<script>` in the `<head>` — **before** the main CSS loads — that reads `localStorage` and sets the `data-theme` attribute immediately.
- For first-time visitors with no stored preference, respect `prefers-color-scheme` as the default.

### 3.4 Component Audit Checklist
Dark mode breaks quietly in places that aren't obvious from the design system alone. Specifically check:
- `.card-glass` — the translucent white background needs a separate dark-mode rgba value, or glass cards will look like white smudges on a dark page.
- Any image/illustration with a white or transparent background that assumes a light page behind it.
- Form inputs, dropdowns, modal backgrounds, and table row striping.
- Toastr notification styling.
- All three dashboards (candidate/employer/admin) — these are easy to forget since they're not in the public-facing screenshots.

### 3.5 Testing
Every page listed in Sections 5–7 of this guide must be manually checked in both light and dark mode before sign-off.

## 4. Global Interaction & Feedback Patterns

### 4.1 Inline Form Validation
Replace "submit then show a generic error popup" with real-time inline validation (red border + helper text beneath the field) across registration, login, contact, and job-posting forms.

### 4.2 Skeleton Loading States
Apply universally — desktop and mobile — anywhere data is fetched asynchronously: job listing grids, course catalog grids, job detail sidebar cards, category/location hero stat cards, "Similar Jobs"/"Related Courses" sections, and dashboard widgets.

- Build skeleton placeholders that match the final content's dimensions exactly, to avoid layout shift (CLS) when real content swaps in.
- Show the skeleton while the fetch is in flight; swap to real content on success; fall through to the empty state (4.3) if the response is empty, or to an error state if the request fails.
- Lazy-load all thumbnail/card images regardless of skeleton state.

Example shimmer pattern:
```css
.skeleton {
  background: linear-gradient(90deg, #eee 25%, #f5f5f5 37%, #eee 63%);
  background-size: 400% 100%;
  animation: skeleton-shimmer 1.4s ease infinite;
  border-radius: var(--border-radius-md);
}
@keyframes skeleton-shimmer {
  0% { background-position: 100% 50%; }
  100% { background-position: 0 50%; }
}
```
Remember to define a `[data-theme="dark"] .skeleton` gradient variant too — the light-gray shimmer above will look wrong on a dark background.

### 4.3 Empty / Zero-Result States with Suggested Alternatives
Trigger conditions: job search/filter returns 0 results, course catalog filter returns 0 results, or a category/location page currently has 0 open roles.

Required elements:
- A friendly illustration or icon (not a blank table row).
- A clear message (e.g. "No jobs match these filters").
- A primary CTA to reset/clear filters, or "Set a job alert" for this search.
- **Suggested alternatives**, pulled dynamically — not guessed by the frontend. The backend should return a small "suggestions" payload alongside any zero-result response, e.g. the top 3 categories or nearby locations that currently *do* have open roles, or trending searches. The frontend renders whatever the API returns; it should never hardcode fallback suggestions.

This same pattern applies to dashboard data grids with zero rows (e.g. an employer with no applicants yet) — friendly message + a relevant CTA (e.g. "Promote this job") instead of a blank table.

### 4.4 Saved Items
- Bookmark/save icon must visibly fill or change state when a job/course is saved.
- Provide a dedicated "Saved Jobs/Courses" tab in the candidate dashboard reflecting the same data.

### 4.5 Trust Tooltips
Add hover tooltips to "Verified" employer badges briefly explaining the verification/KYC process, to reinforce platform trust signals already present in the design (the "Verified employers" messaging on the homepage).

### 4.6 Pagination
Replace small numeric pagination links with an asynchronous "Load More" button or infinite scroll on job listing and course catalog pages.

## 8. Native Mobile App Feel

The goal of this milestone is that on a phone the platform should feel like an installed app, not a shrunk-down website: thumb-reachable actions, swipe-up sheets instead of page jumps, momentum scrollers, and tactile press feedback. The original brief for this section was written in Tailwind shorthand (`active:scale-95`, etc.); **our stack is Bootstrap 5 + jQuery + Tabler Icons**, so every pattern below is specified in that idiom. Reuse Bootstrap's built-in **Offcanvas** component for sheets and drawers (it already ships with the focus-trap, backdrop, and ESC/scroll-lock behaviour we'd otherwise hand-roll) and the design tokens from Section 2 — do not introduce a new CSS framework or a second carousel library for this.

A PWA shell already exists in the repo (`manifest.json`, `sw.js`, `browserconfig.xml`). Treat 8.7 as polishing that shell, not building a new one.

### 8.0 Mobile Foundations (do these once, before the component work)
- **Breakpoint convention.** "Mobile" in this section means `< 768px` (Bootstrap `md` and below). Use Bootstrap's responsive utilities (`d-none d-md-block`, `d-md-none`) and `@media (max-width: 767.98px)` — pick that single boundary and apply it consistently so the desktop and mobile treatments never both render.
- **Viewport + safe areas.** Confirm every layout (`layouts/app.php` and the public `<head>`) ships `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`. The `viewport-fit=cover` is required for the notch/home-indicator insets used by the sticky bars and drawer below. Add an `env(safe-area-inset-*)` aware spacing utility:
  ```css
  :root { --safe-bottom: env(safe-area-inset-bottom, 0px); }
  .pb-safe { padding-bottom: calc(1rem + var(--safe-bottom)); }
  ```
- **Touch-target floor.** Every tappable control on mobile must be at least `44×44px` (WCAG 2.5.5 / iOS HIG). Audit icon buttons (save/bookmark, theme toggle, hamburger) — several currently render smaller. This complements the a11y work in Section 1.3.
- **Kill the tap delays and blue flash.** Globally set `touch-action: manipulation;` on interactive elements and `-webkit-tap-highlight-color: transparent;` so taps feel instant and don't paint the grey/blue native highlight.
- **Respect reduced motion.** Wrap the scale/transition feedback (8.6) and any carousel auto-advance in `@media (prefers-reduced-motion: no-preference)`. Users who opt out get the same function with no animation.

### 8.1 Mobile Header & Slide-out Drawer
- Reduce the mobile header to **logo · notification indicator · hamburger** only. Everything else (secondary nav, Training/Recruitment/Career links, the fullscreen toggle) moves into a slide-out drawer.
- The dashboard already has a hamburger (`#mobile_btn` in `layouts/header.php`) wired to the sidebar — reuse that trigger but route it to a **Bootstrap Offcanvas** (`offcanvas-start`) for the drawer rather than a bespoke slide class, so we inherit the backdrop + body-scroll-lock for free.
- The **theme toggle** (Section 3) and the **notification bell with unread badge** (Section 7.1) must remain reachable on mobile — the bell stays in the top bar; the theme toggle can live at the top of the drawer. Don't drop either when collapsing the header.
- Build **both header states** (logged-out public nav and logged-in dashboard nav, per Section 5.1) for mobile — they have different link sets.

### 8.2 Filter Bottom Sheet
- On `find-jobs.php` (and the Training catalog), the `col-lg-3` `.sidebar-filters` column must be hidden below `md` (`d-none d-lg-block`) and replaced by a **floating `Filter` button** — a pill/FAB fixed near the bottom of the results, showing the active-filter count as a badge (e.g. `Filters · 3`).
- Tapping it opens a **swipe-up bottom sheet** (`offcanvas offcanvas-bottom`, rounded top corners, ~85vh max height, internal scroll). Re-parent the *existing* filter markup into the sheet on mobile — do **not** duplicate the filter form, or the two copies will desync. The simplest robust approach: render the filter block once and let CSS/Offcanvas place it (sidebar on desktop, sheet on mobile).
- Sheet footer is a sticky two-button row: **`Clear all`** and **`Show N results`**, where `N` updates live as filters change and is the same dynamically-sourced count required by Section 10 — never a hardcoded number. Apply-on-tap, with the noUiSlider salary control working inside the sheet.
- Add a drag-handle affordance at the top and allow swipe-down / backdrop-tap / ESC to dismiss (Offcanvas gives the latter two automatically).

### 8.3 Sticky Bottom Action Bars
- On **Job Detail** (`job-details.php`) and **Course Detail**, detach the primary conversion action from the right-hand floating card and pin it to the bottom of the viewport on mobile only.
- **Job Detail:** a fixed bottom bar showing a compact summary (salary or deadline) on the left and the **Apply now** button on the right — reuse the existing `data-bs-target="#ModalApplyJobForm"` trigger so the apply flow is unchanged. Pair it with the secondary **Save** icon.
- **Course Detail:** price + **Enrol** button, reflecting the logged-in user's real enrollment state (Section 10) — if already enrolled, the bar becomes **Continue / Go to course**, not "Enrol".
- Implementation notes:
  - `position: fixed; bottom: 0;` with `padding-bottom: var(--safe-bottom)` so it clears the home indicator; give it the soft top shadow and `--bg-white` token so it adapts to dark mode.
  - Add `padding-bottom` to the page's last content block equal to the bar's height so the bar never covers the footer or the final paragraph.
  - Hide the bar (or let it scroll into place) when the in-flow apply/enrol card is already on screen, to avoid a redundant double CTA — an `IntersectionObserver` on the original card is the clean way to do this.

### 8.4 Stacked Hero Search
- The homepage and listing hero search (`.box-filters-job`: Keyword / Location / Category) is a horizontal multi-input row on desktop. On mobile, restack the inputs **vertically inside one floating glass card** (`.card-glass` from Section 2.3), full-width inputs, with a full-width primary **Search** button at the bottom.
- Keep the same field names/IDs so the existing submit handler and the sidebar-filter sync logic in `find-jobs.php` keep working — this is a layout reflow (`flex-column` under `md`), not a new form.
- Location/Category selects should use the native mobile picker (don't force a custom JS dropdown that fights the OS keyboard/wheel).

### 8.5 Horizontal Scrollers (swipeable carousels)
- Convert rigid grid sections into single-row, horizontally swipeable scrollers on mobile: **Top Picks** (Training), **Browse by category / by location** (Homepage, Category/Location pages), the **courses preview**, and **Similar Jobs / Related Courses**.
- Prefer **CSS scroll-snap** over spinning up owl carousel for these — it's lighter, natively momentum-scrolls on touch, and needs no JS:
  ```css
  .mobile-scroller {
    display: flex; gap: 1rem;
    overflow-x: auto;
    scroll-snap-type: x mandatory;
    -webkit-overflow-scrolling: touch;
    scrollbar-width: none;            /* Firefox */
  }
  .mobile-scroller::-webkit-scrollbar { display: none; }   /* hide scrollbar */
  .mobile-scroller > * { flex: 0 0 80%; scroll-snap-align: start; }
  ```
  The `flex: 0 0 80%` peek (showing a sliver of the next card) is what signals "this scrolls" — don't let cards fill 100% width.
- Where owl is already initialised for a section, it's acceptable to keep it; just ensure the scrollbar is hidden and swipe/drag is enabled. Don't run scroll-snap **and** owl on the same element.
- Keep these lazy: the card images inside scrollers must use the lazy-load attribute already mandated in Section 4.2, and skeletons (4.2) should render as horizontal placeholder cards, not a vertical grid.

### 8.6 Touch Feedback & Micro-interactions
- Give every primary tappable element (cards, buttons, pills, save icons) a press state. The Tailwind `active:scale-95` from the original brief becomes a Bootstrap-friendly utility:
  ```css
  @media (prefers-reduced-motion: no-preference) {
    .touchable { transition: transform .08s ease; }
    .touchable:active { transform: scale(.96); }
  }
  ```
- The **save/bookmark** icon must visibly fill/animate on tap (ties to Section 4.4) and fire a `toastr` confirmation (Section 1.2) — never a native `alert()`.
- Bottom sheet, drawer, and sticky-bar entrances should use a short slide/ease (Offcanvas handles this); keep durations ≤ 250ms so the UI feels responsive, not sluggish.

### 8.7 PWA / Install-to-Home Polish
The app-feel is undercut if the installed PWA looks unfinished. Using the **existing** `manifest.json` / `sw.js`:
- Confirm `display: "standalone"`, a correct `theme_color` / `background_color` (wire `theme_color` to `--primary-navy`, and update the `<meta name="theme-color">` per light/dark theme so the OS status bar matches Section 3), maskable icons, and a real `start_url`/scope.
- Add a tasteful **"Install App"** affordance on mobile (the logged-in nav already lists "Install App" in Section 5.1) backed by the `beforeinstallprompt` event, not a dead link.
- Verify the service worker doesn't serve stale CSS after this revamp ships — bump the cache version so users actually get the new design system. Flag separately if `sw.js` caching strategy needs rework; don't silently rewrite it.

### 8.8 Dark Mode & Dynamic Data (cross-cutting reminders for this section)
- The new fixed surfaces — bottom sheet, drawer, sticky action bar, glass hero card — must all be built on Section 2 tokens and verified in **dark mode** (Section 3.4 explicitly calls out `.card-glass` and modal/offcanvas backgrounds). A sticky bar hardcoded to white will glow on a dark page.
- Every count surfaced in these mobile components — the filter-sheet **"Show N results"** badge, the active-filter count, the job/course figures in the sticky bar — is subject to Section 10: **pulled live, never hardcoded.**

### 8.9 Mobile QA additions
Beyond the cross-cutting checklist in Section 12, this milestone must verify:
- Bottom sheet and drawer trap focus, lock body scroll, and dismiss via swipe-down / backdrop / ESC.
- Sticky action bar clears the home indicator (safe-area inset) and never overlaps the footer or the in-flow CTA.
- Filter sheet and sidebar share one source of truth — changing a filter in one is reflected in the other; the result count is live.
- Horizontal scrollers snap, hide their scrollbars, and momentum-scroll on a real device (not just DevTools emulation).
- No double CTA: the in-flow apply/enrol card and the sticky bar are not both prominent at the same scroll position.

## 10. CRITICAL: No Hardcoded Figures — Dynamic Data Requirements

**Every number, count, or statistic visible in the supplied mockup screenshots is illustrative only.** They are mockup placeholder values, not real data. Nothing in this list should ever be hardcoded into a template, CSS, or JS file — all of it must be sourced from live database queries / API responses at render time, so the figures stay accurate as the platform's real data changes.

Specific instances to wire up, drawn directly from the reviewed mockups:
- Homepage: "Showing 9 of [X] live jobs," every category open-role count (Technology, Finance & Banking, Marketing, etc.), every location job count (Lagos, Abuja, Port Harcourt, etc.), and the "Just Posted" ticker content.
- Jobs listing: total jobs found count, filter checkbox counts (Full Time, Part Time, Contract, Remote), salary range bucket counts.
- Category pages: "Live opportunities" count, "Showing X of Y open vacancies."
- Location pages: "Live jobs" count, "Showing X of Y open vacancies."
- Training marketplace: Active/Free/Paid course counts, "Showing X of Y courses."
- Course detail: related course pricing, and curriculum lock/unlock state per the logged-in user's actual enrollment.

- Testimonials/success stories — confirm with the product owner whether these stay admin-curated content or move to a live reviews system. Don't assume either way.
- Dashboard KPI cards (Section 7.2) — Profile Views, Active Applications, Total Jobs Posted, and any trend indicators.
